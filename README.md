# PromoHunter

Краудсорсинговый сервис отслеживания промоакций сетей общепита: пользователи
отмечают, какие акционные товары (коллаборации, наборы, брендированный мерч)
реально есть в конкретном ресторане прямо сейчас.

Сценарий: найти акцию → узнать, есть ли товар в точке рядом → отметить, что
видел сам.

## Быстрый старт

Нужен только Docker (с Compose v2). Ни Python, ни Node, ни Postgres на хосте
не требуются.

```bash
git clone <repo> && cd PromoHunter
cp .env.example .env
make up          # или: docker compose up --build
```

После старта доступны:

| Адрес | Что это |
|---|---|
| http://localhost:5173 | Фронтенд (dev-режим с HMR) |
| http://localhost:8000/docs | Swagger бэкенда |
| localhost:5432 | PostgreSQL (можно подключиться DBeaver'ом, креды из `.env`) |

Миграции применяются автоматически при старте бэкенда. При первом запуске
(пустая база и `SEED_ON_START=true`) база сидируется тестовыми данными.

**Учётка админа из сидов:** телефон `+79990000000`, пароль `admin123`.
Тестовые пользователи: `+79990000001` … `+79990000004` — пароль у всех
`user123`.

Авторизация — по номеру телефона и паролю. Номер можно вводить в любом
привычном виде (`8 999 000-00-00`, `+7 (999) 000-00-00`) — он нормализуется.
Проверка номера кодом через Telegram — следующий этап: в MVP регистрация
работает без проверки, поле `users.is_phone_verified` под неё уже заложено.

Регистрация открытая. На пустой базе без сидов **первый зарегистрированный
пользователь автоматически получает роль `admin`** — удобно для локального
старта.

## Как пользоваться

После `make up` откройте http://localhost:5173 — данные уже засеяны
(Санкт-Петербург и немного Москвы).

**Как обычный пользователь** (или войдите: `+79990000001` / `user123`):

1. При первом входе выберите **город** — все акции и точки показываются только
   для него. Город хранится в сессии, при регистрации записывается в профиль
   как город по умолчанию (смена в настройках профиля — следующий этап).
   Сменить город в сессии можно тапом по чипу «📍 Город» наверху.
2. **Экран «Акции»** — сети-категории вашего города. Поиск сверху ищет по
   сети, названию акции и товара. Тап по сети → список её адресов (свежие
   отчёты — выше) → тап по адресу → модалка с акциями.
3. В модалке у каждого товара цветной статус («Есть» / «Кончилось» / «Спорно» /
   «Нет данных») и давность последнего отчёта.
4. Стоите в ресторане и видите товар? Жмите **«Отметить наличие»**: по каждому
   товару выберите «Есть» / «Нет» (что не смотрели — не трогайте) → «Отправить».
   Заказали доставку — переключите канал на «Заказывал доставку» (такой голос
   учитывается слабее, особенно «в меню нет»). Статусы обновятся сразу.
   Повторно по той же точке и акции можно через 30 минут (кулдаун).
   Кроме «Есть»/«Кончилось» бывают направленные статусы: «возможно кончилось»
   и «возможно появилось» — кто-то оспорил текущие данные, нужна проверка.
5. **Карта** — точки выбранного города, маркеры в цветах сетей. Сверху — поиск
   по адресу: по умолчанию ищет в вашем городе, для другого города просто
   напишите его в запросе («Москва, Арбат 30»). Тап по маркеру — шторка с
   акциями и той же кнопкой отчёта. «📍» центрирует карту на вас.
6. Навигация — плавающий док внизу, всё в зоне большого пальца. Центральная
   оранжевая кнопка «＋» — **заявить акцию**, которой нет в сервисе: бренд,
   название, товары по одному в строке → уйдёт на модерацию. Статус заявки
   виден в **профиле**.
7. **Рейтинг** — таблица полезности по городам за месяц и за год: очки за
   отчёты, подтверждения, первопроходства и одобренные заявки (и штрафы за
   опровергнутое). Тап по игроку — за что набрано; своя карточка — с полной
   лентой событий. Скрытые веса доверия и механика статусов описаны в
   [docs/trust-and-rating-spec.md](docs/trust-and-rating-spec.md).

**Как админ** (`+79990000000` / `admin123` → Профиль → «Перейти в админку»):

1. **Бренды** — создайте сеть, задайте цвет маркеров.
2. **Рестораны** — добавьте точки сети: клик по карте в форме ставит маркер и
   заполняет координаты.
3. **Акции** — создайте акцию для бренда со списком товаров — она автоматически
   появится во всех точках этой сети.
4. **Заявки** — заявки пользователей, сгруппированные по брендам (12 одинаковых
   заявок видно сразу). «Одобрить» открывает предзаполненную форму акции —
   поправьте и сохраните; «Отклонить» требует комментарий, автор увидит его в
   профиле.
5. **Пользователи** — смена роли и блокировка (заблокированный может читать,
   но не может отправлять отчёты и заявки).

## Make-таргеты

```
make up            # поднять всё (build + up + логи)
make down          # остановить
make restart
make logs          # docker compose logs -f
make sh            # шелл в backend
make sh-front      # шелл во frontend
make migrate       # alembic upgrade head
make migration m="add reports"   # автогенерация ревизии
make seed          # прогнать сиды (идемпотентно)
make psql          # psql внутри контейнера db
make test          # pytest внутри backend
make reset         # down -v + up, полный сброс базы
make prod          # прод-сборка (см. ниже)
```

## Переменные окружения (`.env`)

| Переменная | По умолчанию | Описание |
|---|---|---|
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | `promo` | Креды PostgreSQL |
| `DATABASE_URL` | `postgresql+psycopg://promo:promo@db:5432/promo` | URL БД для бэкенда (host — сервис `db`) |
| `JWT_SECRET` | dev-значение | Секрет подписи JWT, в проде поменять |
| `JWT_EXPIRE_MINUTES` | `10080` | Время жизни токена (7 дней) |
| `STATUS_WINDOW_HOURS` | `24` | Окно агрегации отчётов для статусов |
| `REPORT_COOLDOWN_MINUTES` | `30` | Кулдаун между отчётами одного пользователя по одной паре (точка, акция) |
| `SEED_ON_START` | `true` | Сидировать базу при старте, если таблица users пуста |
| `UID` / `GID` | `1000` | id пользователя хоста — чтобы файлы из контейнеров в bind-mount не были под root (`id -u` / `id -g`) |
| `VITE_API_PROXY_TARGET` | `http://backend:8000` | Куда vite проксирует `/api` в dev |

## Как это устроено

- **Акция принадлежит бренду (сети), а не точке.** Создали акцию для
  «Вкусно и точка» — она автоматически видна во всех ресторанах этой сети
  (связь `restaurant.brand_id == promotion.brand_id`, без копий записей).
- **Отчёты привязаны к конкретной точке.** Статус товара в точке считается
  по отчётам за последние `STATUS_WINDOW_HOURS`; от каждого пользователя
  учитывается только его последний отчёт: `yes > no` → «есть», `no > yes` →
  «кончилось», поровну → «спорно», нет данных → «нет данных»
  (`backend/app/services/status.py`).
- Пользовательские заявки на акции модерирует админ: в админке они
  сгруппированы по брендам, одобрение = создание нормальной акции на основе
  предзаполненной формы.

Стек: FastAPI + SQLAlchemy 2.0 + Alembic + PostgreSQL 16;
React 18 + TypeScript + Vite + Leaflet (OSM). Правила разработки — в
[CLAUDE.md](CLAUDE.md).

## Прод-режим

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
# или: make prod
```

Отличия от dev: backend без `--reload` с несколькими воркерами и без
bind-mount'ов (код копируется в образ), фронт собирается в статику и отдаётся
nginx на порту 80 (он же проксирует `/api`), `SEED_ON_START=false`.

## Частые проблемы

- **`exec /entrypoint.sh: no such file or directory` при старте backend** —
  скрипт получил Windows-переводы строк (CRLF) при клонировании, и шебанг
  сломался. После обновления репозитория уже не воспроизводится (лечится
  `.gitattributes` + зачисткой CRLF в Dockerfile) — достаточно
  `git pull && make up`. На старом чекауте: `git rm -r --cached . && git checkout .`
  или просто заново склонировать.
- **Не получается войти после обновления на телефонную авторизацию** — старые
  аккаунты были привязаны к email и по номеру не войдут. Для локальной
  разработки проще всего `make reset` — база пересоздастся с новыми сидами.
- **Файлы из контейнера принадлежат root на хосте** — пропишите свои
  `UID`/`GID` в `.env` (`id -u`, `id -g`) и пересоберите: `make up`.
- **Backend падает на старте с ошибкой подключения к БД** — дождитесь
  healthcheck базы; entrypoint сам ждёт до минуты. Если база «застряла» после
  жёсткой остановки — `make reset` (сотрёт данные).
- **HMR не подхватывает правки** — в `vite.config.ts` уже включён
  `usePolling`; если правили конфиг, перезапустите контейнер:
  `docker compose restart frontend`.
- **Порт занят (5432/8000/5173)** — остановите локальные сервисы на этих
  портах или поменяйте проброс в `docker-compose.yml`.
- **Поменяли `requirements.txt` / `package.json`, а внутри контейнера ничего
  не изменилось** — зависимости ставятся при сборке образа: `make up`
  (пересоберёт) или `docker compose build backend|frontend`.
- **429 «Вы уже отмечали эту акцию здесь»** — это кулдаун
  (`REPORT_COOLDOWN_MINUTES`), защита от спама, а не ошибка.
